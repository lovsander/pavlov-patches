# Fortran 2018 порт PAPPA

Piecewise Adaptive Poly-Patch Approximation (PAPPA) на Fortran 2018 (gfortran) —
**порт завершён**: ядро метода, пайплайн, проверка конформанс-векторов и
самопроверка перенесены и проходят ворота `verify_all.ps1`.

**Без зависимостей**: только компилятор gfortran, внешних библиотек нет. JSON
(разбор + запись), форматирование чисел, чтение/запись файлов и обход каталогов —
свои. Проверено на **GNU Fortran (tdm64-1) 10.3.0** (TDM-GCC, `C:\TDM-GCC-64`).

## Сборка и запуск

```powershell
powershell -File fortran/build_fortran.ps1            # собрать модули и программы в fortran\build и fortran\bin
powershell -File fortran/build_fortran.ps1 -Test      # + тесты (tests/test_json.f90) и selftest.exe, сборка с -fcheck=all
powershell -File fortran/build_fortran.ps1 -Vectors   # + проверка конформанс-векторов (src/conformance.f90)
powershell -File fortran/build_fortran.ps1 -Clean     # пересобрать с нуля
```

Прогон пайплайна и числовая сверка с референсом Python:

```powershell
.\fortran\bin\pappa.exe --input python\synthetic_data.csv --out-dir samples\synthetic_sphere_fortran --name synthetic_sphere --quiet
python python/studies/verify_port.py --py-dir samples/synthetic_sphere --cpp-dir samples/synthetic_sphere_fortran
```

Скрипт сам ищет `gfortran.exe`: `PATH` → `C:\msys64\{mingw64,ucrt64,clang64,mingw32}\bin`
→ `C:\TDM-GCC-*`. Компиляция идёт ИЗ `fortran\build` (gfortran кладёт `.mod` и `.o`
в текущий каталог, поэтому в флагах стоят `-J. -I.`), диагностика каждого модуля
складывается в `build\<модуль>.err`, а коды возврата — в `build\compile.log`.

Флаги: `-std=f2018 -O2 -Wall -static` и контроль границ `-fcheck=bounds`;
тестовая сборка (`-Test`) строже — `-fcheck=all`. `-static` нужен, чтобы `.exe`
не требовал `libgfortran-*.dll` рядом с собой.

Тест JSON-модуля можно запускать и вручную — он принимает корень репозитория
аргументом (без аргумента берётся текущий каталог):

```powershell
.\fortran\bin\test_json.exe .
```

## Заметки по совместимости (что реально укусило)

* **Главная ловушка: РЕКУРСИВНЫЙ производный тип ломает кучу.** Узел JSON, внутри
  которого лежит массив таких же узлов, на gfortran 10.3 падает с `0xC0000374`
  (повреждение кучи) уже на пробе: глубокое копирование в элементы массива и
  освобождение вложенных аллокатов не выдерживают (`mini_rec`/`mini_rec2`/
  `mini_rec3` в пробных прогонах). Поэтому дерево JSON хранится ПЛОСКО:
  узлы лежат в одной арене (`json_doc%pool`), а связи между ними — ЦЕЛЫЕ ИНДЕКСЫ
  в пул. Глубоких копий и вложенных аллокатов нет вообще, рекурсия осталась
  только в ВЫЗОВАХ обхода (`json_render`, разбор), где она безопасна.
* **`size()` нераспределённого компонента при `-O2` ненадёжен** (и после
  `move_alloc` тоже): проба со `size()` «залипала» на нуле. Вместимость пула
  ведётся СВОИМ счётчиком (`json_doc%cap`), а не `size()`.
* **Форматный `write` на Windows печатает CRLF**, поэтому JSON пишется ТОЛЬКО через
  `access='stream', form='unformatted'`: переводы строк остаются LF и файлы
  совпадают с другими портами побайтно. Чтение сделано так же.
* **`es0.d` (нулевая ширина поля) в gfortran 10.3** печатает 18 значащих цифр
  независимо от `d`, поэтому мантисса берётся с ЯВНОЙ шириной (`es40.d`, `e3`).
* **Внутренняя запись в строку с ОТЛОЖЕННОЙ длиной не распределяет её**
  («End of record»), поэтому все внутренние записи идут в буферы фиксированной
  длины — как в остальных портах.
* **`nint()` округляет половину ОТ нуля**, а режим `int` в остальных портах — к
  ЧЁТНОМУ; для этого в модуле сигналов есть `sig_round_even`.
* **`jp_object`/`jp_array` обязаны быть `recursive`**: они рекурсивно вызывают
  `jp_value`. Без этого ключевого слова gfortran строит неверный кадр, и ловится
  это ТОЛЬКО `-fcheck=all` (не `-fcheck=bounds`) — с тех пор тестовая сборка
  идёт с `-fcheck=all`.
* **Строка ФИКСИРОВАННОЙ длины в JSON уезжает с хвостовыми пробелами.** Поля
  модели объявлены как `character(len=N)` (например `coord_mode` = 16), и без
  `trim` в `dw_str` в документ попадало `"normalized      "`. Читатели Python
  такое значение уже не принимают:
  `coord_mode: ожидается 'normalized' или 'raw'`. Ошибка не видна ни в
  текстовом просмотре документа, ни в сверке чисел — поймал только
  `verify_port.py`.
* **Тесты не привязываются к значениям, которые перегенерируются.** `test_json`
  сверял `created` из `sample.json` по точному значению
  (`2026-09-25T21:01:34Z`) и падал после первого же `verify_all.ps1 -Full`
  (образец перезаписывается) — теперь проверяется ФОРМАТ ISO-8601 UTC
  (`ГГГГ-ММ-ДДTЧЧ:ММ:ССZ`). По той же причине у путей сверяется ХВОСТ
  (`python\synthetic_data.csv`), а не абсолютный путь из манифеста.
* **Дополнение строки пробелами циклом — бесконечный цикл.** У строки
  фиксированной длины `pad = trim(pad)//' '` НЕ увеличивает `len_trim`
  (присваивание дополняет хвост пробелами), поэтому
  `do while (len_trim(pad) < 46)` крутится вечно (в `conformance.f90` так
  зависал вывод). Колонки выравниваются строкой ОТЛОЖЕННОЙ длины через
  `repeat`.
* **`build_fortran.ps1` считает ЛЮБОЙ вывод в stderr ошибкой сборки.** А
  gfortran в `stop 0` печатает «STOP 0» именно в stderr, поэтому успешные
  программы завершаются `stop` без кода. По той же причине убирались ложные
  `-Wmaybe-uninitialized` на дескрипторах аллокатов: пустые массивы/строки
  инициализируются явно (`allocate(x(0))`, `s = ''`).
* Сборка проверяла и другие варианты представления дерева (пробы `mini_arena*`,
  `mini_rec*`) — в репозиторий они не попали, вывод выше описан словами.
* Собранные `fortran/build` и `fortran/bin`, а также `*.mod` в git не попадают
  (см. корневой `.gitignore`).
