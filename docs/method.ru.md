# Метод PAPPA — формальное описание

[English](method.md) · **Русский**

PAPPA (**P**iecewise **A**daptive **P**oly-**P**atch **A**pproximation, aka «Pavlov
patches») — компактная параметрическая модель одномерного сигнала: замкнутый
(периодический) профиль `r(φ)` описывается набором **перекрывающихся локальных
полиномиальных патчей** с **адаптивной степенью**, которые сшиваются
**нормированной smoothstep-разбиением единицы** (непрерывно, C¹ — без скачка
производной на швах), в **нормированной локальной координате** `x = Δ/half_train ∈
[-1, 1]`. Узкие глубокие дефекты (ямы, трещины) могут нести **дополнительные
члены базиса** — усечённые гауссианы, вместо вынужденного роста степени полинома.

Документ этого описания — `docs/README.md`; контракт сериализации —
`spec/`, числовые ожидания — `spec/conformance/`, языковые реализации — по папкам
портов.

---

## 1. Обозначения

| Символ | Смысл |
|--------|-------|
| `φ` | угол вдоль замкнутого профиля, ° (один оборот 0…360, `φ = 360 ≡ 0`) |
| `r(φ)` | измеренный радиус (мм) — вход метода |
| `N` | число патчей (по умолчанию `7`) |
| `i` | индекс патча, `0 … N-1` |
| `sector = 360 / N` | угловая ширина сектора, ° |
| `half_sector = sector / 2` | половина сектора, ° |
| `c_i` | центр патча, ° |
| `half_train = half_sector + overlap_train` | полуокно ОБУЧЕНИЯ, ° (по умолчанию `overlap_train = 15`) |
| `half_use = half_sector + overlap_use` | полуокно ПРИМЕНЕНИЯ (сшивки), ° (по умолчанию `overlap_use = 5`) |
| `d = |Δ|` | угловое расстояние до центра патча по кольцу, ° |
| `x = Δ / half_train` | локальная координата патча, `[-1, 1]` (`coord_mode = normalized`) |

Ключевое: **обучение шире применения** (`half_train > half_use`). Патч видит
больше данных, чем ему «разрешено» изображать, поэтому на краю своей зоны
применения он опирается на данные, а не на экстраполяцию.

## 2. Раскладка патчей

```
sector     = 360 / N
half_sector= sector / 2
c_i        = (i * sector + half_sector + phase_deg) mod 360      (i = 0 … N-1)
```

`phase_deg` (по умолчанию `24.75`) поворачивает всю сетку: узлы (швы между
секторами) уводятся от зон, где измерение заведомо сложное (например, от трещин:
шов — единственное место, где модель не опирается ни на один свежий центр патча).
`phase_deg = 0` — историческое поведение «первый сектор начинается с нуля».
Раскладка ОДНА на всё тело (не своя фаза под каждую яму) — так проще и
воспроизводимее, а выигрыша от подгонки фазы нет.

Проверка на синтетике (10 сечений, детектор `band` — §8): минимальный отступ
«центр ямы → ближайший шов» по всем сечениям равен **+9.92°** при
`phase_deg = 24.75°` и **+0.19°** при `phase_deg = 0`, где шов ближе 2° к трещине
в 5 сечениях из 10 (в самой трещине — ни в одном). Это и есть весь смысл сдвига:
шов не «спасается» от трещины, а получает запас. Картинка и таблица по сечениям —
§14, `docs/assets/method_star.png`.

Угловое расстояние считается по кольцу:

```
Δ(φ, c) = wrap180(φ - c)        wrap180(u) = ((u + 180) mod 360) - 180
d       = |Δ|
```

Маска обучающего окна патча `i`: точки, для которых `d ≤ half_train` (кольцо
разворачивается на ±360°, поэтому окно корректно переходит через 0°/360°).

## 3. Базис патча

1. **Полином** по нормированной локальной координате:

   ```
   p_i(x) = Σ_{k=0..deg_i} a_ik · x^k
   ```

   `deg_i` — **чётная** степень (`deg_min … deg_max`, по умолчанию `4 … 14`).
   Нормировка `x = Δ/half_train` — не косметика: на `deg = 14` в сырых градусах
   матрица МНК плохо обусловлена, в `[-1, 1]` — нормально.

2. **Члены фичера ям** (опционально, §5): `Σ_j amp_ij · g(|Δ - dx_ij|)` —
   усечённый гаусс с центром в `dx_ij` (угол ямы минус центр патча).

Коэффициенты `a_ik` хранятся в документе **по убыванию степени**
(`coefs[0]` — при `x^deg`, `coefs[deg]` — свободный член; оценка по Горнеру
слева направо). Это порядок `numpy.polyfit`/`polyval` — все реализации должны
читать массив именно так (в C-порте это `pp_polyval`).

Легендарное поле `amplitude_scale` (`180.0`) сохранено только для совместимости
форматов: раньше по нему выбиралась степень, сейчас на выбор степени оно НЕ влияет
(осталось справочной метрикой в документе).

## 4. Выбор степени патча: правило RMSE-«локтя»

Степень выбирается **по остаткам на обучающем окне** (не по размаху амплитуды: та
мера измеряет размер, а не сложность формы, поэтому недооценивала узкие глубокие
ямы и переоценивала пологие широкие секторы).

```
вход: angles, radii, center c_i, half_train
mask   = d ≤ half_train                                  # кольцо, ±360°
x      = wrap180(angles - c_i)[mask] / half_train        # ∈ [-1, 1]
y      = radii[mask]
если |x| < 5:  степень = deg_min; метрики RMSE = 0

для deg = deg_min, deg_min+2, …, deg_max:                # только ЧЁТНЫЕ
    a_deg   = argmin ‖V(x)·a - y‖₂                       # МНК (numpy.polyfit)
    rmse_deg= sqrt(mean((V(x)·a_deg - y)²))
rmse_best = min rmse_deg;  best = соответствующая степень

limit    = rmse_best · (1 + deg_elbow_tol)               # deg_elbow_tol = 0.05
deg_i    = наименьшая чётная deg, для которой rmse_deg ≤ limit
           (страховка: если такой нет — best)
```

Смысл: берём **самую дешёвую** степень, которая уже почти так же хороша, как
лучшая доступная (в пределах 5 %). Так «занятые» секторы (с ямой у края, с
перегибом) берут 10–14, а гладкие — 4–6, причём решение принимается локально, по
своему окну, а не глобально по профилю.

Метрики решения пишутся в документ: `metrics.rmse_selected_mm`,
`metrics.rmse_best_mm`, `metrics.n_train_points`, `metrics.deg_elbow_tol`.

**Проверяемость документа** (`validate_model`): степень обязана быть чётной и
лежать в `deg_min … deg_max`, а `rmse_selected_mm ≤ rmse_best_mm · (1 + tol)` —
то есть документ сам доказывает, что степень выбрана по правилу, а не «на глаз».

Что правило даёт на практике (сечение 0, окно патча ≈ 1337 точек из 5882, уровень
шума в окне ≈ 0.12 мм): гладкие патчи берут `deg_min = 4`, «занятые» — 8, 10 и 12;
кривые RMSE(deg), пороги `best·(1.05)` и цена выбора — в §14 и на
`docs/assets/method_degrees.png`. Важно понимать границы: правило оптимизирует
**бюджет**, а не абсолютную точность — однородный `deg = 14` на всех патчах даёт
меньшую ошибку, но за 109 коэффициентов вместо 65 и с МНК на `x^14` в каждом окне.

## 5. Фичер ям: усечённый гаусс в базисе патча

Назначение: узкая глубокая яма на 1–6° требует высокой степени полинома, если
её «нести» полиномом. Вместо этого она описывается **отдельным членом базиса** —
гауссианом, форма которого задана явно.

Параметры (по умолчанию): `sigma_deg = 3.0`, `core_sigma = 2.0`,
`window_sigma = 3.2`, `pit_min_amp = 3e-3` мм, `tapering = true`.

Форма как функция углового расстояния до центра ямы `d` (°):

```
core   = core_sigma  · sigma_deg = 6.0°      (внутри — вес 1: дно не искажаем)
window = window_sigma· sigma_deg = 9.6°      (на границе — ровно 0)

g(d) = 1                                    , d ≤ core
     = s(t),  t = (window - d)/(window - core), s(t) = t²(3 - 2t)
                                            , core < d < window
     = 0                                    , d ≥ window
```

Ядро — тот же гаусс `exp(-d²/(2σ²))`, а «хвосты» заменены smoothstep-спуском:
он даёт **нулевую производную на обоих концах**, поэтому при выходе члена в ноль
в базис не появляется излом (без этого в точке 3.2σ видны ступеньки). Внутри
ядра (≤ 2σ) форма совпадает с чистым гауссом, то есть дно ямы описывается точно.

Как член попадает в патч:

```
для каждой общей ямы j с центром m_j:
    если |wrap180(m_j - c_i)| ≤ window_sigma · sigma_deg:      # окно 9.6°
        добавляется столбец базиса:  g(|Δ - (m_j - c_i)|)
```

(то есть в нормированных единицах патча — `sigma_norm = sigma_deg / half_train`,
`dx_norm = dx_deg / half_train`; так же считается и при оценке модели).

МНК решается на расширенном базисе `[полином deg+1 столбцов | гаусс-столбцы]`.

**Отсечка невидимых ям:** после решения гаусс выкидывается, если
`max |amp_j · g|` по обучающему окну патча меньше `pit_min_amp = 3e-3` мм —
иначе каждое касание окна тратило бы параметр и портило обусловленность.

Раскладка ям — общая для всего тела (одна фаза), центры ям лежат в
`global.pit.centers_deg`; в патче хранится только `{dx_deg, amp}` в
`patches[i].pit_terms`.

## 6. Сшивка: нормированное smoothstep-разбиение единицы

Модель — не «выбор ближайшего патча», а **взвешенное среднее** перекрывающихся
патчей с весами, образующими разбиение единицы:

```
w_i(φ) = 1                                          , d ≤ half_sector
       = s(t), t = 1 - (d - half_sector)/(half_use - half_sector)
                                                    , half_sector < d ≤ half_use
       = 0                                          , d > half_use

r̂(φ) = Σ_i w_i(φ) · v_i(φ) / Σ_i w_i(φ)
```

где `v_i` — значение патча (полином + его гауссовы члены) в точке `φ`.

Свойства, из-за которых выбран именно smoothstep:

* **партиция единицы** — сумма весов нормируется, поэтому константа
  воспроизводится точно, а швы не «садятся» (никакого накопления ошибки по кольцу);
* **C¹** — `s(t) = t²(3-2t)` имеет нулевую производную в обоих концах, значит на
  каждой границе зоны применения (`d = half_sector`) и на внешнем крае
  (`d = half_use`) вес приходит/уходит гладко — скачка производной нет;
* **локальность** — вдали от центра патча его вклад строго нулевой, поэтому
  выброс в одном секторе не «тянет» профиль в соседних.

Так как `half_train > half_use`, на краю зоны применения патч опирается на данные
обучения, а не на экстраполяцию — это и есть причина «обучение шире применения».

## 7. Препроцессинг-1: авто-очистка выбросов (iqr)

Порядок в пайплайне: **сначала очистка, потом детектор ям и модель** (иначе
выбросы «съедают» и выбор степени, и амплитуды ям).

```
baseline = скользящая МЕДИАНА по кольцу, окно = window_points(baseline_deg = 1.0)
res      = radii - baseline                     # остаток: форма снята
center   = median(res)
spread   = IQR(res) = P75(res) - P25(res)
denom    = spread, если spread > 1e-12, иначе 1.0            # в мм (!)
severity = |res - center| / denom
mask     = severity > iqr_k                                  # iqr_k = 3.0 (усы Тьюки)

предохранитель: если помечено больше cap = floor(0.5 · n) точек, оставляем
                cap самых «тяжёлых» (по severity), остальные не выбросы
```

Медиана по **кольцу** (профиль замкнут: окно, вылезающее за 360°, заворачивается
на 0°), окно — нечётное число точек (§11). Метод `iqr` — штатный; в референсе
есть и другие (`gmm`, `hampel`, ручной legacy), они оставлены для исследований и
сравнений.

Известное свойство (сознательное): при идеально гладких данных `IQR(res) → 0`,
`denom` упирается в `1.0 мм`, и очиститель фактически отключается (порог 3 мм).
Для данных с шумом это не мешает, для «стерильных» — мешает (см.
`spec/conformance/README.md`).

Цена отказа от очистки (сечение 0, 2 % инжектированных выбросов): `iqr` убирает
118 точек из 6000 (1.97 %, порог 0.3902 мм при `IQR(остатка) = 0.1301 мм`), после
чего модель берёт степени `[8, 10, 4, 12, 4, 12, 4]` и даёт max|Δr| 0.0542 мм /
RMSE 0.0151 мм. Та же модель **на грязных точках**: степени «уезжают» в
`[6, 8, 4, 8, 4, 8, 4]`, max|Δr| 0.124 мм, RMSE 0.0313 мм — в 2.3 и 2.1 раза хуже.
Картинка — §14, `docs/assets/method_cleaning.png`.

## 8. Препроцессинг-2: детектор ям (band, двухмасштабная медиана)

Идея: яма — структура, которую «видит» узкая медиана, но не видит широкая.

```
narrow = медиана по кольцу, окно = window_points(1.0°)    # узкая
wide   = медиана по кольцу, окно = window_points(10.0°)   # широкая
band   = |narrow - wide|
band   = скользящее СРЕДНЕЕ по кольцу, окно = window_points(2.0°)   # сглаживание
s      = robust_sigma(band) = 1.4826 · MAD(band)
ind    = band / s, если s > 1e-12, иначе 0                # безразмерный «в MAD-ах»
```

Зоны и центры:

```
mask  = ind > k                                            # k = 5.5
зоны  = непрерывные участки mask, границы — angles[i] ∓ step/2,
        где step = медианный шаг сетки; кольцо замыкается (зона, доходящая
        до 360° и начинающаяся с 0°, — одна зона);
        зоны короче min_zone_deg = 2° отбрасываются
центры ям = середины зон
```

Найденные центры и есть `global.pit.centers_deg` — вход фичера (§5).

## 9. Пайплайн «папка образца»

Полный путь от измерения до документа (реализован в референсе и во всех портах):

```
CSV (section_id, height_mm, angle_deg, radius_mm [, radius_ideal_mm])
  │
  ├─ по каждому сечению:
  │    1. очистка выбросов            (auto iqr, §7)        → y_clean, n_outliers
  │    2. детектор ям по y_clean      (band, §8)            → центры ям, зоны
  │    3. модель: раскладка (§2) + степени (§4) + фичер (§5) → патчи
  │    4. контрольная RMSE на равномерной сетке 6000 точек против
  │       идеального профиля (radius_ideal_mm) — метрика отчёта, не обучения
  │
  └─ запись: samples/<имя>/sample.json + sections/<NN>.pappa.json
```

Параметры по умолчанию (единый источник — `python/pappa/core/pit_feature.py`:
`MODEL_DEFAULTS`, `PIT_DEFAULTS`, `DETECTOR_DEFAULTS`):

| Параметр | Значение |
|----------|----------|
| `n_patches` | 7 |
| `phase_deg` | 24.75 |
| `deg_min … deg_max` | 4 … 14 (чётные) |
| `deg_elbow_tol` | 0.05 |
| `overlap_train` / `overlap_use` | 15° / 5° |
| `coord_mode` | `normalized` |
| `sigma_deg`, `core_sigma`, `window_sigma` | 3.0°, 2.0, 3.2 |
| `pit_min_amp`, `tapering` | 3e-3 мм, `true` |
| очистка | `auto` / `iqr`, `baseline_deg = 1.0`, `iqr_k = 3.0` |
| детектор | `band`, окна 1° / 10° / 2°, `k = 5.5`, `min_zone_deg = 2°` |

## 10. Сериализация и что она гарантирует

* **`sections/<NN>.pappa.json`** (формат `pappa v2.0`) — по документу на сечение:
  `global` (единицы, раскладка, политика степени, блок `pit`) + `patches[]`
  (`center_deg`, `degree`, `coefs`, `metrics`, `stats`, `pit_terms`) +
  `statistics`. Схема: `spec/pappa.schema.json`.
* **`sample.json`** (формат `pappa-sample v1.0`) — манифест образца: единицы,
  `config` (все параметры метода), список сечений с относительными путями,
  `input.csv` + `sha256` (след данных, на которых обучено).
* **`report/verify.json`** — числовой отчёт сверки порта с референсом.

Документ — не «набор точек», а описание метода: любой язык воспроизводит контур по
`coefs` + `pit_terms` + раскладке, без доступа к исходным измерениям.

## 11. Численная сторона: допуски и ловушки паритета

**Допуски** (единый контракт, `spec/conformance/README.md`):

| Что | Допуск |
|-----|--------|
| контур `r̂(φ)` | `1e-6` мм — главный критерий (это и есть метод) |
| коэффициенты патчей | `|Δc| ≤ max(1e-8, 1e-9·|c|)` — абсолютный `1e-9` неверен: разные корректные МНК-решатели (SVD в numpy, QR Хаусхолдера в портах) расходятся на ~1e-9 |
| детектор, очистка | доля точек (`frac = 0.02`) — зона на самом пороге может дрогнуть на точку |
| центры ям | `1e-6°` |

**Ловушки при переносе на новый язык** (собраны по 16 портам; проверяйте их, а не
«похожесть кода»):

1. **Индексация.** Массивы в документе 0-базные; в языках с базой 1 ломается
   граница окна (`≤ n` против `< n`) — проверять на CSV, а не на маленьком векторе.
2. **Округление половины.** «К чётному» (banker's): Python 3, R, VBA `Round`,
   Julia `round`, F# `round`, C# `Math.Round`, `Math.rint` в JVM-портах,
   `math.RoundToEven` в Go. «От нуля»: C/C++ `round`, Fortran `nint`,
   Octave `round(2.5) == 3`, Go `math.Round`, Rust `f64::round`, Swift `.rounded()`;
   «к +∞» — JS `Math.round`. В FPC `Round` документирован как банковский, но порт на
   него не полагается (свой `RoundTiesEven`), а в Octave целые в JSON пишутся через
   `printf('%.0f')`, который округляет половину К ЧЁТНОМУ (у порта это отдельный
   тест). Влияет на число точек окна (`window_points`) и на выбор степени.
   Про .NET-миф: у `Math.Round(x)` без второго аргумента половина уже уходит
   К ЧЁТНОМУ (`Math.Round(2.5) == 2`, `round 2.5 = 2` в F# — проверено), поэтому
   `MidpointRounding.ToEven` там пишут для читаемости, а эмулировать приходится
   обратные случаи (`f64::round` в Rust, `math.Round` в Go, `round` в C).
   В Octave `round(2.5) == 3`, зато `printf('%.0f')` округляет половину К ЧЁТНОМУ —
   на нём и записаны целые в JSON (у порта это отдельный тест).
3. **Знак остатка.** В Python `%` неотрицателен (floor-деление), в C/C#/JS — знак
   делимого. Кольцевые разности (`wrap180`, `d`) требуют floor-семантики.
   В Octave операторов два: `mod` (floor, как в Python) и `rem` (знак делимого) —
   годится только `mod`.
4. **Порядок коэффициентов** — по УБЫВАНИЮ степени (`coefs[0]` при `x^deg`,
   схема Горнера слева направо).
5. **Медиана и процентили.** Медиана чётного набора — среднее двух средних;
   `P25/P75` — линейная интерполяция (`numpy.percentile`, «type 7»), а не
   «ближайший ранжированный элемент».
6. **Окно по углу.** `w = int(round(span_deg / шаг))`, затем нечётное (`| 1`),
   минимум 3, максимум `n` (при чётном `n` — `n-1`); шаг — медиана положительных
   разностей углов.
7. **Замкнутость.** Все фильтры — по кольцу; окно, вылезающее за границу, должно
   заворачиваться, а не обрезаться.
8. **`Σw` и NaN.** Если сумма весов нулевая (вырожденная раскладка) — `NaN`, а не 0.
9. **Формат чисел в JSON.** Нужна кратчайшая запись, дающая round-trip (в R-порте
   для этого написан поиск, в Python — `repr`). `%.17g` сверку тоже проходит, но
   документы становятся нечитаемыми и «грязными» в diff.
10. **CSV.** BOM, CRLF, пробелы; проверка «достаточно ли колонок» —
    `число_колонок < нужного` (в 1-базных языках легко сместиться на день).
11. **Порядок ключей JSON.** Должен совпадать с референсом (побайтовый diff
    документов — удобный первый тест); `null` (например `"detector": null`)
    должен пережить запись — в R `x[[k]] <- NULL` удаляет элемент, нужно
    `x[k] <- list(v)`.
12. **Локаль машины.** Числа в документах и CSV обязаны быть с точкой: в JVM
    помогает `Locale.setDefault(Locale.ROOT)`, в .NET —
    `<InvariantGlobalization>true</InvariantGlobalization>` в `.csproj` плюс
    `CultureInfo.InvariantCulture` в парсерах и форматтерах, иначе ru-RU даст
    «8,73e-11» и запятую как разделитель дробной части.
13. **Булевы значения в JSON.** `true`/`false` — только нижний регистр, а
    `StringBuilder.Append(bool)` в C# печатает `True`/`False` (в JS
    `String(true)` — правильно, в Pascal свой `BooleanToString`). Ошибку ловит
    `python spec/check_schema.py`: значения сверяются со схемой.
14. **Окно фильтра — это не только ширина, но и выравнивание.** В 1-базных языках
    окно по кольцу пишется как `mod(i − h − 1 + (0:w−1), n) + 1`: потерянная «−1»
    сдвигает медианный фильтр и сглаживание на точку каждое, а вместе — на две.
    Ловит это вектор детектора: зоны встают на 2° раньше эталона (у Octave-порта
    заодно вылечились 5 «потерянных» выбросов очистки из 9).
15. **Implicit expansion (Octave/MATLAB).** `1×k .* k×1` — не ошибка формы, а
    матрица `k×k`: в обратном ходе МНК `sum(a(i, k:n) .* x(k:n))` тихо возвращает
    вектор, и присваивание скаляру падает далеко от места ошибки. Пишите
    `строка * столбец` (или явные формы), а не `.*` со смешанной ориентацией.
16. **Значение против ссылки.** Там, где в R спасало окружение (передача по
    ссылке), а в Julia — `mutable struct`, в Octave структура КОПИРУЕТСЯ:
    «мутаторы» обязаны возвращать объект (`m = model_fit(m, ...)`), счётчики
    тестов — тоже (`[passed, failed] = check(...)`). Забытое присваивание не
    ломает ничего явно — просто считается старое состояние.
17. **Пустое поле структуры.** `struct('f', {})` в Octave/MATLAB создаёт 0×0
    МАССИВ структур (а не структуру с пустым полем), и обращение к полю падает
    с «Invalid call to numel». Пустой список в поле — `struct('f', {{}})`.
18. **Строка ФИКСИРОВАННОЙ длины уезжает в JSON с хвостовыми пробелами.** В
    языках с такими строками (Fortran `character(len=N)`, Pascal `string[N]`)
    запись поля без `trim` даёт `"coord_mode": "normalized      "`. Числовая
    сверка и текстовый просмотр документа этого не видят — падает только
    строгий загрузчик (`coord_mode: ожидается 'normalized' или 'raw'`).
    Там же: дополнение строки пробелами ЦИКЛОМ бесконечно — у строки
    фиксированной длины `pad = trim(pad)//' '` не увеличивает `len_trim`,
    выравнивание делается строкой переменной длины (`repeat`).

19. **Существование пути и скрытые каталоги (VBA).** `Dir(path, vbDirectory)` не
    возвращает скрытые каталоги (`C:\Users\<user>\AppData` скрытый), поэтому
    проверка «каталог есть?» врала и `MkDir` вызывался по уже существующему
    каталогу — ошибка 75 «Path/File access error». Там же: у `Dir` с атрибутами
    путь с хвостовым `\` даёт ошибку 52, а `Dir(path, vbDirectory)` считает
    совпадением и обычный файл. Наличие проверяется `GetAttr` (бит
    `vbDirectory`), отсутствие — ошибками 53/76. Отдельно: **рабочий каталог
    Excel — `Documents`**, а не каталог запуска, поэтому относительные пути
    обязаны быть абсолютными (иначе папка образца появляется в «Документах»).
20. **Числа и файлы в VBA.** `Format$`/`Str` печатают не больше 15 значащих цифр
    (`1/3` даёт `.333333333333333`) — побайтовый round-trip документа недостижим,
    сверять надо с допуском `1e-14` отн.; `NaN`/`Inf` в языке не существуют
    (`0/0` — ошибка 11, переполнение — ошибка 6), поэтому нулевой знаменатель
    ветвится явно (в порте нулевая сумма весов даёт 0, как в C); `Open ... For
    Output` пишет файл в ANSI (cp1251) — порт печатает только ASCII, а не-ASCII
    строки уходят как `\uXXXX`; в русской локали `Format$` ставит запятую, а
    `CDbl` от строки `1.5` даёт ошибку 13, поэтому числа разбираются через `Val`.

21. **Порядок компиляции — часть языка (F#).** В F# файл видит только объявленное
    ВЫШЕ: циклических ссылок между файлами нет, forward-деклараций внутри файла нет,
    типы обязаны стоять до класса, который их использует. Поэтому список `<Compile>`
    в `.fsproj` задан явно (`EnableDefaultCompileItems=false`) — иначе SDK добавит
    `*.fs` по алфавиту и сборка упадёт на «not defined». Там же: в F# нет
    `break`/`continue`/раннего `return` (циклы переписываются флагами: разбор
    аргументов CLI, поиск RMSE-«локтя»), нет автосвойств (`let mutable` + `member …
    with get() and set()`), а члены класса видят друг друга только через
    self-идентификатор (`member this.X`, не `member _.X`).
22. **`sprintf` и `ToString` в .NET смотрят в разные стороны (F#).** В F#
    printf-форматы инвариантны к культуре (`sprintf "%f" 1.5` → `1.500000` даже при
    `ru-RU`), а `ToString()`/`Parse()` — нет (`1,5`). В C# ровно наоборот. Итог:
    `CultureInfo.InvariantCulture` обязателен в каждом `ToString`/`Parse`, но не в
    `sprintf`. Отдельно: `sprintf "%.2e"` печатает по-сишному, с ТРЁХЗНАЧНЫМ
    порядком (`8.73e-011`), тогда как numpy/Python — `8.73e-11`; для диагностики,
    сравнимой с соседними портами, нужен свой формат (`"0.00e+00"`).
    Там же (PowerShell, не F#): функция вида `& $app …; return $LASTEXITCODE`
    захватывает в свой выход ВЕСЬ вывод приложения, и проверка кода возврата врёт —
    надёжнее собирать команду в массив и читать `$LASTEXITCODE` напрямую.

Приёмка порта: все векторы `spec/conformance` в допусках **и** совпадение папки
образца с референсом численно (`verify_port.py`), плюс свои тесты/`selftest`.

## 12. Как это проверяется одной командой


То же без PowerShell (Linux/macOS/Git Bash) — `tools/verify_all.py` на stdlib-Python 3:

classpath, `dotnet pappa.dll` вместо apphost). `--os posix --dry-run` печатает
POSIX-команды, ничего не запуская, `--list` — точные команды своей ОС. Строка `vba`
в POSIX-прогоне отсутствует: VBA 7 живёт внутри Excel, а Excel есть только на Windows.

Порты без тулчейна на машине помечаются `SKIP` и не считаются провалом.

| все патчи deg 14 | 109 | 4.873e-02 | 1.217e-02 |
| **PAPPA (степень по патчам)** | **65** | **5.416e-02** | **1.511e-02** |

(65 = 61 полиномиальный коэффициент + 4 ямных; в таблице сравнения методов выше
у PAPPA стоит 61 — там считались только полиномы.)

Честное чтение: адаптивная степень — это выбор **бюджета**, а не абсолютного
максимума точности. При похожем бюджете она лучше любой однородной степени вдвое
(deg 8, 67 коэффициентов: max|Δr| 1.061e-01 против 5.416e-02), по max|Δr| не хуже
однородного deg 12 при 95 коэффициентах (оба 5.416e-02, потому что максимум ошибки
сидит на дне ямы, где работает ямный член), но строго точнее адаптивной только
deg 14 — 4.873e-02 за 109 коэффициентов (1.7× бюджета) и с МНК на `x^14` в каждом
окне, то есть с худшей обусловленностью.

### 14.3 Очистка: что дала бы модель без неё

Сечение 0: 6000 точек, `iqr` (k = 3.0) убирает 118 (1.97 %), порог по остатку
0.3902 мм при `IQR(остатка) = 0.1301 мм`, медианное окно по кольцу 1.0° (17 точек).
Выбросы разбросаны по всему кольцу, поэтому «пропустить» их детектором нельзя.

| Модель (те же детектор, раскладка и правило «локтя») | Степени | max\|Δr\|, мм | RMSE, мм |
|---|---|---|---|
| обучена на ОЧИЩЕННЫХ точках | `[8, 10, 4, 12, 4, 12, 4]` | 5.416e-02 | 1.511e-02 |
| обучена на ВСЕХ точках (без очистки) | `[6, 8, 4, 8, 4, 8, 4]` | 1.240e-01 | 3.127e-02 |

Выбросы «съедают» сразу два решения: степени проседают (8–12 → 6–8), потому что
МНК в окне тянется за выбросами, и ошибка растёт в 2.3 раза по max|Δr| и в 2.1 раза
по RMSE. Поэтому очистка в пайплайне идёт ПЕРВОЙ — до детектора, до правила «локтя»
и до самого МНК.
